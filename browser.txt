브라우져는 다양한 구성요소로 구현됨
- 렌더링 엔진
- js 엔진
- 네트워크 요청을 처리하는 엔진

다양한 기능을 수행
- 도메인 주소를 IP주소로 변환
- HTML등의 리소스 로딩
- https 커넥션을 맺게 네트워크 요청
- 로컬 스토리지 / 세션 스토리지 / 쿠키등의 저장소 관리

여러 기능을 의미있는 단위로 나누어 관리함

UI
- 브라우져 상단바 영역에 해당하는 부분
- 주소 표시줄 / 내비게이션

UI 백엔드
- OS환경에 따라 기본적인 UI 요소를 그리는 인터페이스 제공
- 드롭다운 / 다이얼로그 / 스크롤 바

브라우져 엔진
- 내부의 서로다른 요소들사이의 연결고리 역할
- 각 구성요소과 독립적으로 기능하면서도 상호작용할 수 있게 조율
- UI 주소창에 url 입력시 네트워크 인터페이스와 상호작용하여
  요청을 생성하고 응답 처리후 렌더링 엔진에 적용
- JS엔진과도 상호작용

렌더링 엔진
- 브라우저 엔진이 여러 인터페이스와 상호작용하여 가져온 페이지를 화면에 시각적으로 표현
- HTML, CSS를 해석하고 처리하여 결과를 픽셀 그래픽 형태로 렌더링

- 렌더링: 문서구조와 스타일 정보를 결합하여 표현
- 렌더링 엔진은 webkit과 gecko가 있음

네트워킹 엔진
- 네트워크 요청을 처리하는 역할
- HTML, CSS, JS, Image, font등의 리소스 요청
- 브라우져에서 요청을 보내야 할떄 요청을 보내고 응답을 처리
- 보안상의 이유로 HTTP대신 암호화 레이어가 추가된 HTTPS 권장

자바스크립트 엔진
- JS코드를 해석하고 실행하는 역할
- DOM과 CSSOM을 조작해 화면에 그려지는 요소를 조작
  - 실행 후 렌더링 엔진과 상호작용

데이터 영속성
- 쿠키 / 로컬스토리지 / 세션 스토리지/ 캐시등의 기술을 활용해 페이지와 관련된 데이터를 저장
- 쿠키 인증방식은 브라우져에 세션정보를 저장하고 매요청마다 이정보를 네트워크 요청에 포함

브라우저의 구성요소는 별도의 프로세스 or 쓰레드로 이뤄짐
- 브라우저 각 탭은 별도의 프로세스임
- 달라질 수 있지만 멀티 프로세스 모델을 사용하여 역할과 책임을 분리한다
- 각 탭을 분리하여 한 탭이 죽어도 나머지 탭은 유지되게 (프로세스는 별도의 메모리 공간과 실행흐름을 가지므로)
- 또한 격리를 통해 다른 기능끼리의 악용을 방지
- 유지보수도 용이하며 반응성 향상

브라우저가 화면을 렌더링 하는 과정을 알아보자

------------------------------------------------------

1. DNS 주소 => IP주소
- DNS가 가리키는 목적 서버의 IP주소를 알아야 한다
- 도메인 주소는 사람이 이해하기 쉬운 alias
- 컴퓨터간 소통에는 IP주소가 필요

- DNS 리졸브: DNS 주소를 IP주소로 바꾸는 주소 변환 과정
- 변환된 IP주소의 웹서버로 GET요청을 보내고 HTML을 응답받아 렌더링

DNS(Domain Name System)
- 도메인 이름과 IP 주소를 연결하는 거대한 전화번호부
- 여러 계층으로 나뉜 분산 시스템으로 구성되며 도메인도 계층구조임

도메인 계층구조
ex) account.qanda.ai

Top Level Doamin(ai)
- 도메인 이름 가장 오른쪽
- 주로 특정 기관이나 조직, 국가를 표현
- 새로운 TLD 등록은 엄청 비쌈

Second Level Domain(qanda)
- Second Level Domain
- 페이지의 이름을 나타냄(기업명, 서비스명)
- TLD내부에서 유일무이해야함
- TLD와 SLD를 결정하여 도메인 등록기관에 연결해야함

SubDomain (account)
- TLD와 SLD안에서 여러개 정의될 수 있는 하위 도메인
- 조직내의 특정 부서나 서비스를 구분하고자 사용

도메인이 위와 같이 계층화되어있으므로 매핑정보도 분산 저장된다
도메인 이름과 IP주소사의 매핑 데이터를 DNS 레코드라고 함
네트워크 요청을 최소화하고자 브라우져와 브라우저가 설치된 호스트와 네트워크등 여러 레이어에 캐싱

브라우져-호스트머신에 캐싱되어있지 않다면 로컬 DNS서버로 DNS 레코드 요청 
로컬 DNS서버에도 없으면 로컬 DNS서버가 루트 DNS에 쿼리하여 TLD서버 위치를 찾음
TLD서버에 요청을 보내 서브도메인의 매핑정보를 들고 있는 SLD서버의 위치는 어디인지 응답받음
SLD서버는 특정 도메인과 서브도메인에 대한 전체 데이터를 가져 요청시 IP주소를 제공

이를 통해 호스트, 브라우져, 로컬 DNS에 DNS 레코드가 캐싱됨
DNS캐싱은 주로 로컬 DNS서버에서 이뤄지긴함
로컬 네트워크 라우터에도 캐싱되는구만

포트 
- 항구
- 서버의 IP주소와 더불어 포트를 알아야 프로세스가 실행하고 점유하는 포트번호를 알아야 됨
- http와 https는 기본적으로 80, 443의 포트번호를 지정

오리진: 리소스를 가져올 서버를 유니크하게 식별하는 정보
- 스킴(https) + hostName(domain) + port
- 3가지 구성요소가 하나라도 다르면 크로스 오리진
- 크로스 오리진간의 리소스 공유를 브라우저가 제한하는 정책이 CORS

사이트
- 쿠키를 사용하면서 등장한 개념
- 쿠키와 같은 웹 리소스가 공유되는 범위제한을 오리진보다 너그럽게 하기 위한 개념

크로스 오리진으로 인식되도 same site일 수 있음 (eTLD + 1이 일반적으로 site를 의미)
- api.turtlechain.io ==samesite== page.turtlechain.io

DNS리졸브로 IP+PORT는 알아내었다.
근데 HTTP는 취약하다
HTTPS를 써야하는데 보안 연결을 맺는 과정이 필요하다

웹은 초기에 정보공유를 목적으로한 public한 성격의 readOnly 플랫폼
- HTTP는 보안이 고려되지 않음, 평문 데이터가 패킷으로 전달됨
- 통신의 주체인 브라우저와 서버가 암호화/복호화하는 방법을 둘이서만 공유
  보내기전에 암호화하고 받으면 복호화하면 된다

https는 브라우저와 서버간 공통된 세션키를 만드는 과정을 먼저 거친다 (TLS 핸드쉐이크)
이를 사용하여 암호화/복호화를 처리

비대칭 키 암호화: public key와 private key를 사용
- public key를 암호화에 사용
- private key를 복호화에 사용
- cpu 리소스 사용량 많음
- 따라서 최초 보안 연결 맺을때는 비대칭 키를 사용하지만 맺은 이후에는 대칭키인 세션키를 사용

대칭 키 암호화
- 하나의 키로 암호화 복호화를 모두 수행

클라에서 보안연결을 요청하는 메시지를 보냄(tls버전 + 알고리즘 + 키교환 방법 제안)
서버가 제안 정보를 보고 선택한 내용 + 자신의 공개키가 담긴 SSL 인증서를 응답
클라에서 인증서 검증
클라에서 자신과 서버에서 생성한 난수를 이용해 프리마스터 시크릿을 생성하고
이것을 웹서버의 공개키로 암호화하여 서버에 전송
서버는 프리마스터 시크릿을 자신의 개인키로 복호화하여 같은정보를 가지게 됨
이를 통해 서버와 클라가 같은 세션키를 가짐

이제 HTTPS 보안도 잡혔다. 이제 HTML 응답받는다.

HTTP 요청 헤더에는 요청에 대한 내용과 지원하는 압축 알고리즘등을 포함
브라우저는 응답 헤더의 Content-Type 필드를 보고 확장자를 판단
Content-Encoding으로 압축 알고리즘 파악
Cache-control 필드를 보고 캐싱여부를 판단


HTML파일을 전달받았으니 html파일을 위에서 아래로 읽어가며 해석하자 (파싱)
- DOM 트리 구축
  - html 문자열을 파싱하여 노드 객체를 만들어 메모리에 저장
  - 노드의 트리구조를 구축
- script만나면 파싱 멈추고 js실행

- 각 노드는 tagName, attribute, style, children으로 구성
- 기본적으로 node는 3가지 종류 
  - document node : 최상위 노드
  - element node
  - text node

DOM
- 문서의 요소가 가진 계층 구조를 표현하는 객체 모델
- 요소에 접근하고 조작하는 방법을 제공
- HTML은 정적인 표현 => DOM은 동적인 표현
- 구조화된 객체 표현인 DOM Tree
- 이벤트 리스너를 붙히거나 스타일을 적용 가능

DOM Tree가 구축되면 DOMContentLoaded 이벤트 발생
- 아직 화면에 그려지진 않은 상태임
- 아직 cssom트리는 미완성
- load이벤트는 돔 트리 구축 + 이미지나 외부 스타일시트까지 모두 로드된 경우 발생

-----------------------------------------------------

!! 스타일 요소도 파싱해서 구조화해야한다 !!
- CSSOM은 스타일들을 구조화한 객체 모델
- cssom은 css문서의 구조적 표현으로 볼 수 있다 (선택자+스타일)

css는 위에서 아래로 흐른다는 의미의 단계적 속성을 가진다 (cascading)
- 규칙이 위에서 아래로 흐르듯이 적용
- 규칙이 겹치는 경우 어떤 규칙이 우선해서 적용되는지 결정
- 중요성(!important) => 구체성(id vs class) => 정의된 순서

브라우져는 기본 css스타일을 가지고 있다.
- 이를 균일화하기 위해 reset.css를 설정하곤 한다 (스타일 정규화)

DOM Tree와 CSSOM 트리를 바탕으로 렌더트리를 구성
- 렌더 트리는 실제로 화면에 나타나야 하는 요소들의 계층구조
- blink라는 엔진이 렌더트리를 구성
- head태그 같이 눈에 안보이는 건 렌더트리에 미포함 + display: none인것들도
- float나 position:absolute인 요소는 DOM트리의 위치와 다르게 처리된다.
  (문서 흐름에 벗어난 것들이므로)
- 아무튼 DOM Tree와 1대1 매핑되진 않음

-----------------------------------------------------

렌더 트리를 구축했으니 실제로 그려야 하는건 파악되었다

레이아웃 계산
- 렌더트리에서 각 요소를 뷰포트의 어떤 좌표에 어떤 두께로 그려야 하는지를 계산
- 렌더트리의 루트 노드부터 재귀적으로 실행
- DOM 업데이트로 인해 이 계산과정을 DOM의 일부혹은 전체에 대해 반복하는것이 reflow
- 레이아웃을 계산하는건 여러 맥락이 고려되는 비싼 연산
- 박스 모델을 기반으로 연산

페인트
- 무엇을 어떻게 그릴지를 기록하는 단계
- 렌더트리를 기반으로 그리는 순서와 스타일을 결정
- 각 요소를 어떤 순서와 어떤 스타일로 그릴지 Paint Commands(Display List)를 생성한다.
- 아직 실제 픽셀을 생성하는 단계는 아님

- 쌓임 맥락을 기반으로 요소를 그리는 순서를 결정
- 브라우저는 각 요소를 3차원의 레이어로 구성하므로 요소가 다른 요소보다 위인지 아래 인지를 공간정보를 결정해야 표현가능

쌓임맥락
- 가상의 z축을 사용한 html요소의 3차원 개념화
- 사용자가 브라우저를 위에서 아래로 내려본다고 가정하고 요소의 위아래여부를 개념화
- 자식요소는 부모요소의 쌓임 맥락 내부에서만 의미를 가짐
- position / z-index / ...

-----------------------------------------------------

브라우져가 내부 기준으로 요소들을 레이어로 분리한다
- 레이어를 분리하는 기준은 주로 css속성 (transform, opacity, filter, animation)

픽셀화: 각 레이어를 GPU가 이해하는 형태인 픽셀 단위의 데이터로 변환
컴포지션: 픽셀화된 여러 레이어를 하나의 완성된 프레임으로 결합하는 최종단계

이를 하나의 프레임으로 결합하여 최종 스크린샷을 생성한다
- 스크롤하거나 레이어의 일부가 바뀐 경우에는 레이어의 위치만 조정하고 컴포지션

크롬과 크로미엄의 차이는?
- 크로미엄은 오픈소스 프로젝트
- 크로미엄자체는 기본 브라우저 기능만 제공
- 여기에 여러 기능을 추가 보완하여 크롬과 같은 브라우져가 제공됨

크롬은 크로미엄을 기반으로 한 상용버전 웹 브라우저
- 크로미엄에 추가기능 / 디자인 변경 / 보안패치등을 포함
- 즉 크로미엄은 핵심기능을 포함하는 코어고 각 브라우저는 여기에 개선사항을 적용

세부구현은 제각각이여도 브라우저가 지켜야하는 표준 인터페이스가 있음
- 국제 웹 표준단체에서 웹 표준 인터페이스를 결정

W3C: html, css, svg, 웹접근성 가이드라인등의 표준 개발
- HTML5, CSS, DOM을 표준화했음

WHATWG
- HTML, DOM, Fetch API등 웹표준의 리빙 스탠더드를 제공
- 지속해서 업데이트 되는 온라인 명세를 관리

IETF
- HTTP, TLS, WebRTC등의 프로토콜과 관련된 RFC 발행
- 도메인 네임에서 IP주소를 획득하는 DNS resolve나 보안 레이어가 추가된
  HTTPS의 같은 네트워크 명세

ECMA 인터내셔널
- ECMAScript, JSON을 표준화
- 핵심 기능남능ㄹ 정의하므로 호스트 환경에서 제공되는 기능은 정의 X

특정 브라우져는 어떤 속성을 미지원하거나 버전이 낮은경우에 폴리필이 필요할 수 있다.
- 폴리필은 브라우저간 미세한 구현차이나 미지원 기능을 보완하고자 사용하는 코드조각
  - 이전 버전 브라우저에서도 동일한 기능을 사용할 수 있도록 보완해주는 코드
  - 이미 지원하는 브라우저에서는 영향을 미치지 않게 설계
  - 좋긴한데 임시방편이기도 하다
  - 브라우저의 명세와 구현이 분리되므로 등장
- 크로스 브라우징의 피로함 ㅠㅠ

js 엔진 성능이 많이 발전했지만 과도한 연산은 프레임 드롭을 발생시키곤 한다.
메인 프로세스에서 렌더링과 js실행을 같이 처리하므로 js가 오래 실행되면 렉걸림

!! 한 프레임에서 처리되는 js의 양을 조절하자 !!

메인 스레드에서 실행하는 연산을 적절히 나누어 효율적으로 실행

1. requestAnimationFrame
- 브라우저의 다음 렌더링 타이밍에 맞춰 콜백을 실행하도록 예약한다.
  - 브라우저는 렌더링 루프에 맞춰 requestAnimationFrame 콜백을 실행한다.
  - 일반적으로 디스플레이의 주사율(예: 60Hz, 120Hz)에 맞춰 호출된다.
- DOM 변경이 없더라도 브라우저의 렌더링 루프에 맞춰 콜백은 실행될 수 있다.

- 화면을 갱신하는 작업을 브라우저의 렌더링 타이밍과 동기화하기 위해 사용한다.
- 화면 갱신과 동기화되어 애니메이션이나 DOM 업데이트에 적합하다.
- 콜백 실행 시간이 길면 프레임 드롭이 발생할 수 있다.

2. requestIdleCallback
- 브라우저가 유휴(Idle) 상태일 때 콜백을 실행
- 사용자 입력이나 렌더링보다 우선순위가 낮은 작업에 적합
- 브라우저가 계속 바쁘면 실행이 지연되거나 실행되지 않을 수도 있음

위의 2가지도 결국 메인스레드에서 처리되어 성능 향상을 못할수 있다.
- 워커를 통해 브라우저에서 무거운 연산을 메인스레드가 아닌 백그라운드 스레드에서 실행하게 하자
- 메인스레드는 UI와 인터랙션을 처리하게 하고 무거운 연산은 워커가 처리하여 반응성을 향상
- 구현의 복잡성과 호환성 문제가 있긴함
- 워커에서는 DOM에 접근못함
